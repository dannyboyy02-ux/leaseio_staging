1 · The one root cause

Every defect on that screen traces to a single structural fact:

An active lease in a governed edit session is rendered with the first-time-intake-review chrome. When you click Unlock, model_locked flips to false; the locked read-view early-return (LeaseReview.tsx:2728) is skipped; and the whole finalized record falls through to the extraction-review workbench — green "approve to advance" strip, red/amber alarm borders, per-row "View in document", "not extracted" captions, per-tab "Reviewed" pills, and a red "Cancel". None of that is true for a live lease whose only pending task is "change a value and submit it for approval."

The fix is therefore not a new page — it's teaching the existing workbench that lifecycle_status === 'active' && isUnlockedDraft is a distinct, calm mode, and routing every review-only signal through that gate. The two surfaces that already speak the right language (the amber "Editing — N changes" chip and the "Submit for approval" button) become the whole story; everything else gets quieted.

2 · What we are NOT changing

  • Locked active read view. model_locked === true && active already early-returns to LockedLeaseDetail (LeaseReview.tsx:2728-2729) — the calm "on file" record. That path stays; it's the baseline the unlocked-edit state should feel like.
  • First-time intake review. A brand-new extraction should show confidence borders, source links, and the review/approve funnel — that's the human auditing the AI. We only suppress those signals once the lease is active.
  • The governance model. One open change set per lease, maker-checker submit → approve/reject, server-side lifecycle writes — all unchanged. This is purely the presentation + post-action navigation layer.
  • The concurrency guard (#158, partial unique index + 409s) shipped already; untouched here.

C1 · Make the status strip lifecycle- and change-set-aware

Current: deriveState() branches only on isProcessing / canApprove / isApproved / modelLocked. On an unlocked active lease modelLocked === false → it falls into the first-time 'ready' branch and renders "Ready to approve — Approve to advance." It has no idea the lease is already active or that we're in an edit session.

Target: pass lifecycleStatus + isUnlockedDraft + stagedItemCount into the strip. Add an edit-session branch above the approval branches; suppress the approval/lock language entirely when the lease is already active.

6 · H7 — where the user goes after submit / rejection (researched)

You asked me to research this rather than decide it for you. The key realization from the research: "submission" and "rejection" are different kinds of event and can't share one redirect. Submission is synchronous (the user is right there, having just clicked Submit). Rejection is asynchronous (a different person acts minutes or hours later — the submitter isn't on the page, so there's nothing to redirect). They need different treatments.

6.1 — After the submitter clicks "Submit for approval" (synchronous)

User clicks Submit for approval → submit_change_set (re-locks lease, change set → pending_approval)
↓
Success toast: "Changes submitted to {approver} for approval. You'll be notified when they decide."
↓
Redirect to the list the user came from — Leases by default, Dashboard if that's the referrer.

Recommendation: return to the list they came from, defaulting to /app/leases, not the Dashboard. The SaaS convention for finishing work on one record is "back to the list you came from," supported by breadcrumbs — not a jump to a generic dashboard. The Dashboard is an overview/landing surface; after a focused edit the user's mental context is "the portfolio I was working through," which is the Leases list. Implementation is referrer-aware so we honor where they actually started:

// after a successful submit_change_set:
const from = (location.state as any)?.from;            // set when navigating into the lease
toast.success(t('review.submitted_for_approval', { approver }));
navigate(from === 'dashboard' ? '/app/dashboard' : '/app/leases');
Why not stay on the page? Post-submit the lease re-locks — staying drops the user on a now-read-only form with no task left (the original strand). Redirecting also matches the Post-Redirect-Get pattern, which research shows cuts accidental re-submits dramatically. If they navigate back to the lease, it now shows a "Changes pending approval" state (with an optional future "Withdraw" affordance — Salesforce-style recall, noted as an enhancement, not in this scope).

6.2 — When the change is rejected (asynchronous)

A redirect can't fire for an event the user isn't present for. The researched pattern is notify + show the verdict on return:

Approver rejects on the Approval Queue → reject_change_set (terminal; lease stays locked with current terms)
↓
Notify the submitter — in-app notification (+ email) carrying the rejection reason
↓
When the submitter next opens the lease → red verdict banner (mock §4.2): who declined, when, the reason, and "the lease keeps its current terms" — with Revise & resubmit / Dismiss

Research is emphatic that the reason must reach the submitter, and that "rejected" must be visually distinct from "approved." The verdict reads the terminal rejected change set (status='rejected' + reviewer note) and renders it; "Revise & resubmit" opens a fresh draft pre-seeded with the declined values so the user isn't retyping.

6.3 — For the approver after they act (Approval Queue)

Distinct from the submitter: after an approver approves/rejects a queue item, the convention is return to the queue (the list of pending approvals) with a confirmation toast — so they can process the next one, email-triage style — not the Dashboard. If they acted from the lease page itself, return them to wherever they came from (queue or Leases).

7 · H6 decision — the "Cancel" exit

You deferred this to me. Here's the call and the reasoning.

Keep the word "Cancel" (you chose it deliberately over "Discard changes"). The misread isn't the word — it's the treatment: it's rendered text-destructive (red) and buried as the first ⋯-menu item directly above "Archive", so it reads as "cancel the lease." Two changes fix that without re-litigating the label:

  1. Strip the destructive-red. Reserve red for genuinely destructive/terminal actions (Archive, delete). Cancelling an edit session is non-destructive — it just discards unsaved staged edits and re-locks; the lease is untouched.
  2. Surface it as a visible inline secondary next to "Submit for approval" at sm+ widths (see mock §4.1), instead of hiding the escape hatch in an overflow menu. Below sm it collapses into the ⋯ menu as a neutral (not red) item — honoring the original responsive concern (LeaseReview.tsx:2916) that the bar mustn't overflow off-screen.
  3. Tighten the confirm dialog copy so the scope is unmistakable: "Discard your unsaved changes? The lease keeps its current terms — nothing is submitted."
// LeaseReview.tsx:2920 — inline non-destructive Cancel at sm+, neutral in ⋯ below sm
<Button size="sm" variant="outline" className="hidden sm:inline-flex"
  onClick={() => setCancelChangeSetDialogOpen(true)} disabled={cancelingChangeSet}>
  Cancel
</Button>
// …Submit button… then ⋯ menu — the menu item loses text-destructive and only shows below sm:
<DropdownMenuItem className="sm:hidden" onClick={() => setCancelChangeSetDialogOpen(true)}>
  <X className="h-4 w-4 mr-2" /> Cancel
</DropdownMenuItem>
