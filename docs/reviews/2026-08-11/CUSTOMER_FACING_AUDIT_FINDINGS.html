LeaseIO Audit — What a Customer Sees

2026-08-11 · theleaseio.com (production, main @ 8ed16aa) · persona: admin in the Labs Analytix Business workspace · method: live UI walkthrough with read-only DB cross-checks · assess-only, nothing fixed

I signed in and used the product the way a finance customer would: submitted a lease request through the full approval chain, uploaded a document for AI extraction, ran archive/delete/restore, asked the AI assistant about the portfolio, checked every displayed number against the database, and re-walked core surfaces in Spanish. The headline: the core workflows and the financial math are solid — the requestor chain completes end-to-end and every dashboard/portfolio figure recomputes exactly. The one serious problem is the flagship AI assistant, which reports a materially wrong portfolio total. Six product findings and one documentation-drift note follow, Critical → Low.

How to read severity

Each rating is impact × likelihood × blast radius. HIGH = a primary workflow blocked for a common case, or materially wrong financial data a finance team would act on. MEDIUM = real friction or minor inaccuracy with a findable workaround. LOW = polish, cosmetic, or convention drift with no decision impact. Every finding was reproduced live and, where it's a number, recomputed independently from the database.

Findings

HIGH #187

Leo (the AI assistant) reports a portfolio total that is ~29% too high and invents the lease count

Leo assistant · supabase/functions/ai-assistant · Business-tier feature

Asked the built-in suggestion "What is the total annual rent commitment?", Leo answered $3,527,481/yr — $293,957/mo across "12 active leases." Neither figure is right. The workspace has 5 active leases and the dashboard and Portfolio both show $228,275/mo ($2.74M/yr). Leo's monthly figure is the base-rent sum across all seven rows whose lifecycle_status='active' — which includes two archived leases that no customer-facing surface counts — and the "12" count is fabricated (it matches no query). This is the product's flagship differentiator ("send us your leases, we'll tell you what's in them") returning a number a finance user cannot reconcile against any screen in the app, and stating it with full confidence.

Leo answered$293,957 / mo · $3,527,481 / yr · "12 active leases"
Dashboard & Portfolio show$228,275 / mo · $2.74M / yr · 5 active
DB: sum(current_monthly_rent) of the 7 active-status rows (incl. 2 archived)$293,956.78 ← Leo's number
DB: genuine active, non-archived leases5

Why HIGH: materially wrong financial data on the headline Business-tier feature, delivered confidently, reconciling with nothing the customer can see — the exact failure the product exists to prevent. Why not Critical: read-only assistant (no data corruption or security boundary crossed), and a careful user could catch it against the dashboard. Likely fix: Leo's data fetch must apply the same scope the UI uses — exclude archived=true, and only count/sum the lifecycle states the portfolio treats as live; the count field should come from that same filtered set, not a model guess.

MEDIUM #188

A signed-in user cannot change language — the EN/ES toggle exists only on the login screen

app shell · Settings → Appearance (theme only) · leaseio.language set at auth

The product ships full English + Spanish, and Spanish renders cleanly once selected (verified below). But the language toggle lives only on the auth pages (login/signup, top-right "EN"). Inside the app there is no language control anywhere — Settings → Appearance offers theme (Light/Dark/System) and nothing else. A Spanish-speaking user who arrives already signed in (e.g. accepted an invite link, or a teammate set up the account) is stranded in English with no way to switch, and an English user can't preview Spanish. For a product that markets bilingual support, the switch is missing from the one place a logged-in user would look.

Why MEDIUM: a whole advertised capability is unreachable for signed-in users, but there's a workaround (sign out, toggle at login) and it doesn't corrupt data. Fix: add a language selector to Settings → Appearance (or the profile menu) writing the same leaseio.language key the auth toggle already uses.

MEDIUM #189

Internal issue-tracker reference is printed in the customer-facing Report settings

Reports → Report settings → "Artifact retention (days)" help text

The help text under the retention field reads, verbatim: "Reports older than this become eligible for cleanup (cron not yet implemented; tracked in KNOWN_ISSUES #12)." A paying customer is shown an internal ticket reference and an admission that the feature behind the setting they're configuring doesn't actually run. Two problems in one line: the jargon leak, and a settable control that silently does nothing.

Why MEDIUM: visible on a standard settings screen, erodes trust (looks unfinished / internal), and the setting is functionally inert. Not HIGH because it's copy, not data or money. Fix: replace with customer-facing language and either wire the retention cron or remove the control until it works.

LOW #190

The same lease appears under two different names on different pages

Leases list & Dashboard (uses request_title) vs Portfolio (uses property_address)

The lease shown as "Northwind Estates" on the Leases list, dashboard, and in Leo appears as "1200 Market Street, Suite 800, San Francisco" on the Portfolio page and its watchlist — because those surfaces render different name fields. To a user scanning both pages, one lease looks like two different properties. Consistent naming (or showing both, e.g. "Northwind Estates — 1200 Market St") would remove the ambiguity.

Why LOW: cosmetic/convention; no wrong number, and both labels are truthful for that lease.

LOW #191

Reports "Monthly Rent Overview" chart is actually plotting total commitment

Reports → "Monthly Rent Overview" chart

The chart titled "Monthly Rent Overview" is subtitled "Total commitment by lifecycle status" and its axis runs to ~$32M — it's charting multi-year total commitment, not monthly rent. Title and content disagree; a reader glancing at the title would misread the magnitude. Retitle to match what it shows (e.g. "Total Commitment by Status").

Why LOW: mislabel, not a miscalculation — the bars are correct for total commitment.

LOW #192

Direct-upload extraction leaves Asset Type blank

Direct upload → process_lease · leases.asset_type null after extraction

A lease added via Upload Document extracted every field at 99% confidence (landlord, tenant, 3,850 sqft, $12,500 rent, dates, security deposit, 3% escalation — all correct), but asset_type came back null. The lease then shows a blank "Type" on the Leases list and in the CSV export, while the same lease added via the request flow shows "Real estate." The document is plainly an office lease, so the type was inferable. Minor, but it's a visible gap in an otherwise-perfect extraction.

Why LOW: one non-critical field, easily set by hand; everything financial extracted correctly.

DOC DRIFT #193

Docs describe self-serve firm onboarding as "not built" — it shipped in June

CLAUDE.md + KNOWN_ISSUES.md #105 vs supabase/functions/create-firm (PR #55/#56)

Not a customer-facing bug, flagged because it will mislead the next session: CLAUDE.md and KNOWN_ISSUES #105 repeatedly state self-serve firm onboarding / firm Stripe checkout is deferred and firms are "operator-created only." But git shows PR #55/#56 (June 2026) shipped self-serve create-firm + hosted checkout, and the deployed function is self-serve for any authenticated user (with a per-owner cap). The source-of-truth docs materially understate shipped capability — worth reconciling per the repo's own "docs are part of the change" rule.

Action: reconcile CLAUDE.md's Phase-10 "deferred" list and #105 to reflect that self-serve firm creation + checkout are built; re-scope whatever genuinely remains.
